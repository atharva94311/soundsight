# ESP32-S3 listening node

Runs the same classifier as the browser twin, on an ESP32-S3 with an INMP441
I²S microphone, and publishes detections over MQTT in the format the twin's hub
already expects.

## Wiring

| INMP441 | ESP32-S3 | note |
|---|---|---|
| VDD | 3V3 | not 5 V |
| GND | GND | |
| SCK | GPIO 4 | bit clock |
| WS | GPIO 5 | word select / LRCL |
| SD | GPIO 6 | data out |
| L/R | GND | selects the left channel, which the sketch reads |

Any GPIOs work; these avoid the strapping pins. Change them at the top of
`vas_soundsight.ino`.

## Build

Arduino IDE or arduino-cli, board **ESP32S3 Dev Module**. Dependencies:
`PubSubClient` (Nick O'Leary). `WiFi`, `esp_now` and `driver/i2s` ship with the
ESP32 core.

Put these in one sketch folder:

```
vas_soundsight/
  vas_soundsight.ino
  vas_dsp.c   vas_dsp.h
  vas_nn.c    vas_nn.h
  model_weights.h      <- generated by ml/export.py, do not edit
```

Then set, at the top of the .ino:

- `NODE_ROOM` / `NODE_NAME` — must match a module in `vas3d/js/config.js`
- `WIFI_SSID` / `WIFI_PASS` / `MQTT_HOST`
- `BEACON_MAC` — print it from the beacon and paste it here
- `ENABLED[]` — which classes this node may raise

`ENABLED[]` mirrors the `classes` array for that module in the twin's config. A
door node reporting baby-cry would contradict the twin's localisation story, so
each node only claims what it is placed to hear.

## What it does

Captures 16 kHz mono continuously into a 1-second ring buffer, and four times a
second computes a log-mel spectrogram and runs the CNN. Detections use the same
policy as the browser (`vas3d/js/audio/listener.js`): a 75% gate, agreement
across 3 of the last 5 inferences, and an 8-second refractory window per class.
A node that behaved differently from the twin would make the twin a lie.

Publishes to `home/<room>/event`:

```json
{"c":"fire","p":0.98,"node":"kitchen","rssi":-54}
```

If the broker is unreachable it falls back to ESP-NOW straight to the beacon —
no phone push, but light, shaker and band still alert. That is the failure mode
the twin models.

Inference is skipped when the room is below `SILENCE_RMS`, which in practice
removes about two thirds of the duty cycle and matters on the 18650.

## Memory

No interpreter and no TFLite Micro: `vas_nn.c` walks the layer table in
`model_weights.h` directly. Batchnorm was folded into the convolutions at
export, so only conv / ReLU / global-average-pool / linear remain.

- weights: int8 with a per-output-channel float scale, ~35 kB flash
- activations: two ping-pong buffers of 16640 floats = **130 kB** total
- everything is statically sized; no malloc in the audio path

Weights are int8 but activations stay float32. That is a 4× flash saving with no
calibration pass and ~1.6e-2 worst-case probability error against PyTorch. Full
int8 activations would cut RAM too, but needs a calibration pass and careful
requantisation — worth doing, not worth getting quietly wrong first.

`vas_nn_required_arena()` recomputes the true peak from the layer table at boot
and **refuses to run** if the model has outgrown `VAS_NN_MAX_ACT`, rather than
letting it scribble past the buffer. If you widen the model, raise that constant.

## Verifying without hardware

The DSP and network compile and run on the host, and are checked against PyTorch:

```bash
cd ml && .venv/bin/python -m tests.test_c_parity
```

That compiles `vas_dsp.c` and `vas_nn.c` with the host compiler, runs known
signals through them, and compares against the trained PyTorch model. Run it
after regenerating `model_weights.h`.
